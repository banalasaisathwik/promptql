# CLAUDE.md — services/api/app/investigations

Path-scoped: applies to investigation domain code (facts, evidence,
planning, hypotheses, code diagnosis).

## Core distinctions

- **Evidence != Fact** — Evidence is source-backed info collected from a
  system; a Fact is a structured conclusion deterministically established
  from evidence ("GitHub diff shows checkout.py changed" is evidence;
  "checkout.py was modified by PR #42" is a fact).
- **Fact != Hypothesis** — a Fact is deterministically supported; a
  Hypothesis is a plausible interpretation that may explain multiple facts.
  Never represent a hypothesis as authoritative fact.
- **Grounded != Proven correct** — grounded means available evidence
  supports the claim; correct means it matches actual ground truth. Real
  correctness needs a gold answer, later operational evidence, human
  confirmation, or successful remediation.
- **Domain result != Runtime run** — `InvestigationResult` is the
  investigation conclusion; run status/timestamps/steps/runtime errors
  belong to runtime lifecycle state, not the pure domain result, unless the
  domain genuinely owns them.
- **Durable persistence != Durable execution** — persisting run
  status/steps/result to PostgreSQL means state survives process memory; it
  does not mean a crashed workflow can resume. Crash recovery,
  reconciliation, replay, and retry-safety are separate concerns.
- **Planner != Executor** — the planner answers "what should we try next?";
  the runtime/executor answers "is that valid, permitted, within budget,
  safe, executable?" Never let planner output bypass deterministic runtime
  validation.
- **Tool registry != MCP** — an internal tool registry can exist without
  MCP. Do not introduce MCP merely because the runtime has tools.
- **Runtime events != OpenTelemetry** — product/runtime events
  (`plan_generated`, `tool_completed`, `evidence_added`,
  `hypothesis_generated`) describe domain execution; OTel describes
  operational telemetry (latency, errors, spans). They may correlate but do
  not replace each other.

## LLM ownership boundary

Different fields have different authorities:

- evidence → connectors/runtime
- typed deterministic facts → deterministic transformation/validation
- candidate hypotheses → may be generated by LLM
- hypothesis grounding status → deterministic validator where possible
- missing information → runtime/planner
- run status/timestamps/errors → runtime
- final `InvestigationResult` assembly → deterministic application code

A domain model is not automatically an LLM output model — an LLM should
receive only a minimized schema (e.g. `HypothesisGenerationOutput`), never
be allowed to manufacture a complete `InvestigationResult` directly.

## Changing LLM behavior in this subsystem

1. Identify exactly which step is probabilistic.
2. Define the structured input boundary.
3. Define the structured output boundary.
4. Treat provider output as untrusted; validate schema, then validate
   semantic/domain constraints separately.
5. Preserve source/evidence references and explicit unknown/abstention
   behavior.
6. Record provider/model/prompt identity safely (no secrets).
7. Keep provider failure distinct from schema failure, validator failure,
   and domain unknown.
8. Add or update evals when behavior materially changes
   (see `docs/TESTING.md`).
9. Never treat successful parsing as evidence a model answer is correct.

Prefer `probabilistic proposal + deterministic control` over
`probabilistic proposal + probabilistic acceptance`.
